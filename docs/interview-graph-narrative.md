# 面试叙事稿：知识图谱从「同步构建」到「可恢复的异步流水线」

> 素材来源：`docs/incident-graphflow-stuck-20260915.md`（真实线上事故）、
> `api/internal/modules/dataset/graphflow/`（现网实现）。
> 用途：简历撰写 + 面试口述。讲述顺序固定为 **痛点 → 动作 → 收益**。

---

## 一、核心命题（一句话）

**把知识图谱构建从"请求链路里的同步操作"，重构成"可持久化、可恢复、可增量更新的异步流水线"。**

支撑这句话的四条工程判断：

1. 长耗时、有中间态、需要重试的副作用操作，**从第一天起就不该放进 HTTP 请求**。
2. 有中间态就必须**持久化中间态**，否则失败只能从零重来。
3. 图数据是**全局共享**的（实体、关系会被多篇文档引用），所以必须有**版本概念**，
   否则重建期间知识库等于没有图谱。
4. 异步化不是把任务丢进队列就结束了，**可观测 + 可自愈**才是异步化的另一半。

---

## 二、30 秒版（电梯陈述）

> 知识图谱这块我主要做了一件事：把它从同步构建改成了异步流水线。
> 原来的图谱构建是跟着接口走的，开启图谱或更新文档时，接口要一路等实体关系抽取、
> 实体对齐、Neo4j 写入全部跑完才返回。真实知识库文档一多，这个接口响应就是分钟级，
> 经常直接超时；而且更麻烦的是没有中间状态，超时之后既不知道跑到哪了，重试也只能
> 从头再来，LLM 抽取白烧一遍。我把它拆成了阶段化的异步任务，接口只返回 run_id，
> 每个阶段的状态、进度、错误都持久化，失败可以只重试失败的那个阶段，服务重启能自动
> 续跑，重建期间旧的图谱版本继续对外服务。

## 三、90 秒版（主叙述，面试主力）

**痛点**

> 原来的知识图谱，功能是有的，但在真实知识库里不好用。根本问题是构建过程跟请求绑在
> 一起：用户开启图谱或者文档更新后，接口要同步等完整条链路——LLM 实体关系抽取、
> 实体对齐、Neo4j 图写入、实体向量化——全部完成才返回。
> 这带来三个后果：
> 第一，接口响应时间不可控，文档一多就是分钟级甚至更久，直接超时，用户看到的是失败，
> 但服务端可能还在跑；
> 第二，整个过程没有中间状态，一次超时或重启，进度就全丢了，重试只能整条重来，
> 重复的 LLM 调用是实打实的成本；
> 第三，图谱是全局共享数据，重建的时候旧数据已经清了、新数据还没建好，
> 这段时间知识库实际上是没有图谱可用的。

**动作**

> 我做了四层改造。
> 第一层是**入口异步化**：构建接口不再同步等待，只创建一次 Graph Run 就返回 run_id 和
> 202，把执行体从请求链路里彻底摘出去。
> 第二层是**阶段化 + 持久化**：把抽取、对齐、图写入、向量同步、可见性投影拆成独立阶段，
> 每个阶段的输入输出、状态、进度、错误码、重试次数全部落库；阶段之间用 Outbox 事件
> 驱动，保证数据库状态和异步派发的一致性，不会出现"状态改了但任务没发出去"。
> 第三层是**版本隔离**：引入 Graph Revision 做单调递增的版本号，区分"当前构建中的版本"
> 和"当前对外可召回的已发布版本"，同一知识库的构建严格串行；任务执行前校验自己是不是
> 当前活跃 Run，被取代的任务直接丢弃，杜绝旧任务覆盖新版本。
> 第四层是**自愈**：运行级租约 + 周期性对账，服务重启后自动扫描未完成的 Run 接着跑，
> 而不是等人来点重建。
>
> 另外针对文档变更，我没有做全库重建，而是基于资产代次和同步批次做增量：新文档的
> ADD 和旧文档的 CLEANUP 编在同一批次里，一个批次里多个文档先各自抽取，全部完成后
> 才合并做一次对齐和一次图写入——避免文档数把全库对齐的开销放大；清理的时候按证据
> 引用计数回收，只有关系没有证据了才删关系、实体没有关系了才删实体，不会误删其他
> 文档还在用的共享实体。

**收益**

> 接口从分钟级等待变成毫秒级返回，并且带阶段级进度，用户能看到"实体关系抽取 60%"
> 而不是干等超时；单个阶段失败只重试那一阶段，服务重启能续跑；重建期间已发布版本
> 继续提供召回，图谱从"重建即不可用"变成"构建期间也不降级"；文档更新不再触发全库重建。

## 四、3 分钟版：深挖「为什么异步化必须配套可观测和自愈」

（面试官说"再展开讲讲"时用。这段来自真实事故复盘。）

> 异步化之后我们踩过一个很典型的坑，值得讲一下。
> 有一次线上知识库的图谱卡在 0%，四个阶段全部显示"等待中"，用户反复点重建也没用。
> 排查下来是一连串问题叠加：
> 一次手工重建失败了，它对应的文档后来被删掉了；新的文档同步进来时创建了一个新版本的
> Run，但这个 Run 因为并发时序问题没有被正确"提升"为执行态，而且这个失败被 defer 里
> 的 fire-and-forget 调用静默吞掉了，没有任何日志。
> 而用户每次点"重建"，系统会优先"续跑"那个旧的失败 Run——但它的文档已经删了，
> 每次续跑都必然失败；因为同一知识库的构建是严格串行的，旧 Run 每次都占住执行槽位，
> 新 Run 永远排不上。所以表现就是"永远 0%，且没有任何报错"。
>
> 这个问题让我补了三件事：
> 一是**错误不能被吞**，提升失败必须记录并且可重试，因为幂等操作重试是安全的；
> 二是**失败 Run 的可续跑性要校验前提**，如果它依赖的文档已经没了，应该直接标记为
> superseded 而不是无脑续跑；
> 三是**加巡检和对账**：数据集存在失败前驱、同时又有更高版本的 pending Run 超过一定
> 时间，就告警。
>
> 我的结论是：异步化真正的难点不在"怎么把任务扔进队列"，而在于**任务的生命周期管理
> ——幂等、顺序、版本、失败语义、可观测**。把长任务异步化只是第一步，让它可诊断、
> 可自愈，才算真的做完。

## 六、追问应对清单

**Q1：为什么之前会做成同步的？**
> 早期是作为"开启开关后的一次性构建"设计的，功能验证阶段文档少、模型调用快，同步能
> 跑通；真实知识库文档量上来后，同一个设计就必然超时。这也是我们复盘后最核心的结论：
> 长耗时、有中间态、需要重试的副作用操作，不该放在 HTTP 请求里。

**Q2：异步化之后怎么保证不重复建、不乱序？**
> 三层。入口用幂等键去重；数据库层面用唯一索引 + 行锁保证同一知识库同一时刻只有一个
> Run 在执行；任务执行前校验 Active Run，被取代的旧任务直接丢弃。版本号单调递增，
> 可见性投影完成前不推进"已发布版本"，所以旧任务永远改不到新版本的图谱。

**Q3：怎么保证异步任务最终一定完成？**
> 状态全部落库，任务和 Run 都有租约；服务启动时以及运行期每 10 秒做一次对账，扫描
> 未完成的 Run，根据各阶段任务的实际状态重新计算进度并推进到终态。所以即使进程被杀、
> 消息丢失，也一定能收敛，不会永久卡住。

**Q4：增量更新怎么保证不误删？**
> 清理是按证据引用计数回收的：删掉旧文档产生的证据后重新统计来源数量，关系没有证据
> 才删关系，实体没有关系才删实体。被其他文档引用的共享实体和关系会被保留。

**Q5：接口改成异步，前端体验怎么保证？**
> 返回 202 和 run_id，前端轮询状态接口，展示四个阶段的进度和状态（抽取/对齐/图写入/
> 向量索引）；失败时给出明确错误码，并提供"重建"和"按文档重试"两个入口。

**Q6：这套改造最难的判断是什么？**
> 是意识到"异步化"只是手段，真正要解决的是**任务生命周期的正确性**：幂等、顺序、
> 版本、失败语义、可观测。只把任务扔进队列，只是把同步的超时换成了异步的静默卡死。

## 七、讲的时候不要碰的三个坑

1. **不要主动说"之前代码很烂/之前没人做异步"**，统一说"早期设计的局限"，
   显得是理性演进而不是抱怨同事。
2. **不要主动提"耗时下降 X%"**（没有实测数据支撑）。收益一律用**语义化的结果**描述：
   接口不再阻塞、失败可续跑、重建期间不降级、不再全库重建。
3. **不要把"异步化"讲成唯一亮点**。你真正的亮点排序是：
   ① 长任务不入请求链路（架构判断）
   ② 版本隔离保证重建期间不降级（对共享数据的理解）
   ③ 增量更新 + 证据级回收（业务深度）
   ④ 可观测 + 自愈（工程成熟度）
   ⑤ 批量/并发/缓存（执行层面的优化）
