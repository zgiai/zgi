# ZGI Agent 工作能力升级：业务方案与分阶段交付计划

## 1. 一页摘要：这次升级要解决什么

- 文档日期：2026-09-26。
- 文档状态：业务设计与推进建议，不代表功能已经上线，也不构成对外服务承诺。
- 面向读者：业务负责人、产品经理、项目负责人、客户成功、合作开发者及试点客户。
- 对应技术方案：[ZGI Agent 执行环境架构设计与渐进改造计划](agent-runtime-architecture-and-roadmap.md)。

本次升级的目标，是让 ZGI Agent 从“回答问题、调用单个功能”，进一步变为“在受控条件下完成一项工作，并交付真实结果”。

用户可以把文件和任务交给 Agent，让它读取资料、使用已启用的技能、分步骤处理、生成结果，并在同一会话中继续修改。开发者可以更容易地把已有脚本和工具带进来，不必为每个功能重新开发一套平台接口。

这不是提供一台无限权限的电脑，也不是承诺 AI 可以处理所有任务。业务方向是：**增加可完成的任务种类，减少重复配置，让结果可获取、过程可控制、费用可解释。**

### 本轮最重要的五个结果

1. 用户得到真实可下载的工作成果，而不只是“已完成”的文字。
2. 一项任务可以分步骤完成，中间文件能够在同一会话中继续使用。
3. 企业可以选择在自己的部署环境运行，或使用批准的托管云环境。
4. 常用工具可以提前准备和复用，减少每次任务重新配置的工作。
5. 新能力逐步开放，不影响现有 Skill 和未启用新能力的 Agent。

### 推进原则

先做本地与托管云的可用版本，再补齐文件保留和工具准备，然后开放受控联网与平台业务调用，最后提供自建虚拟机和正式运营能力。

每一步都必须回答三个问题：用户现在能完成什么、如何证明真的完成、出问题后如何停止或退回。

## 2. 当前业务痛点与预期改善

现有 ZGI 已具备 Agent、Skill、脚本执行、文件输入和结果输出等基础能力。本轮不是推倒重来，而是把这些能力连接成更完整的工作过程。

| 当前痛点 | 对业务的影响 | 升级后的预期改善 |
|---|---|---|
| 一个脚本需要的工具或软件包没有准备好 | 技能导入后仍无法使用，需要研发协助定位 | 提供工具准备和可复用的环境模板，缺少条件时给出可理解的原因 |
| 每次执行相对独立 | 多步骤任务需要重复上传、配置和搬运中间结果 | 同一会话保留工作文件，Agent 可以连续处理 |
| 结果停留在日志或路径中 | 用户不知道成果在哪里，也不能直接交付给同事 | 文件以标准下载入口呈现 |
| 自定义技能适配要求较多 | 合作开发者接入成本高，可用技能增长慢 | 普通带脚本的技能在授权环境内也能运行，不强制补写平台专用声明 |
| 只有一种运行方式 | 客户在部署条件、数据要求和成本之间缺少选择 | 提供本地、托管云及后续自建虚拟机选项 |
| 任务过程、失败和资源使用不够完整可见 | 客服解释困难，业务难以判断可靠性和使用成本 | 显示任务状态、失败原因、文件保留规则和资源额度 |

上述收益是待试点验证的目标，不预先宣称已经提升了某个百分比的效率或成功率。

## 3. 服务对象、使用场景与优先级

### 3.1 服务对象

| 对象 | 最关心的问题 | 本轮提供的价值 |
|---|---|---|
| 业务使用者 | 能不能完成任务，结果能不能拿走 | 用自然语言提交任务、查看状态、下载成果、继续修改 |
| Skill 开发者 | 现有脚本能否复用，缺少工具怎么办 | 更少专用声明、可复用工具准备流程、清晰的权限边界 |
| 企业管理员 | 谁能用，数据去哪里，费用怎么控制 | 按组织和 Agent 授权、明确运行位置、配额与停止能力 |
| 客户成功与运营人员 | 为什么失败，如何帮助客户恢复 | 可理解的失败分类、任务记录、恢复与转人工指引 |

业务使用者不需要为了使用已经发布的 Skill 学习命令行。开发者负责准备技能，管理员负责授权和运行配置。

### 3.2 优先业务场景

第一批场景选择输入清晰、结果可核对、风险较低的文件型工作，不从高风险自动操作开始。

| 优先级 | 场景 | 预期成果 | 最早对应阶段 |
|---|---|---|---|
| P0 | 多份 CSV 数据整理、汇总和格式统一 | 汇总文件、异常记录和文字说明 | M4 |
| P0 | 批量文件检查、文本提取、规则转换 | 处理后的文件及错误清单 | M4；仅限已具备工具的格式 |
| P0 | 在同一会话中追加条件、修改上一轮结果 | 新版成果，无需重复上传全部文件 | M4 |
| P1 | 隔天继续处理已上传的资料 | 恢复工作文件后继续执行 | M5 |
| P1 | 团队反复使用相同的一组处理工具 | 使用准备好的环境模板 | M5 |
| P1 | 开发者接入需要额外软件包的技能 | 经批准准备工具后运行技能 | M6B |
| P1 | 获取批准网站的数据并生成汇总 | 带来源说明的处理结果 | M6A |
| P1 | 脚本与已经授权的平台模型或业务工具协作 | 文件成果与可追踪的业务调用 | M6C |
| P2 | 对外部托管服务有严格限制的企业部署 | 在自有虚拟机环境运行同一类任务 | M7 |

“处理文档或表格”不等于所有格式在第一版都可用。具体格式取决于已准备的工具，应在技能说明中明确列出。

### 3.3 贯穿项目的示范任务

建议以“销售数据汇总”作为统一演示，贯穿本地、云端、文件保留和工具扩展：

1. 用户上传两份销售 CSV。
2. 选择已经发布的汇总 Skill，说明统计口径。
3. Agent 检查字段；缺少关键字段或规则不明确时询问用户。
4. Agent 生成汇总 CSV 和异常记录，页面提供下载入口。
5. 用户补充“再按地区分组”，Agent 基于会话内文件生成新版成果。
6. M5 完成后，用户可以在保留期内回来继续处理。
7. M6 完成后，按授权引入新的处理工具或批准的数据来源。
8. M7 完成后，在自建环境复现同一任务。

验收使用固定样本和预先核对的金额、记录数及分组结果。不以 Agent 自述“处理成功”作为证据。

此任务是试点建议，不将销售分析能力扩展为财务决策或自动写入生产业务系统的承诺。

## 4. 用户会获得怎样的产品体验

### 4.1 使用前

- 新能力默认关闭，由有权限的人为 Agent 开启。
- 用户可以知道当前任务使用企业自己的运行环境，还是批准的托管云环境。
- 用户可以看到本次允许使用的工具、联网范围和基本额度。
- 需要额外工具时，先准备并确认，不在任务执行途中无限制地安装软件。

### 4.2 使用中

- Agent 先理解任务，再检查输入和技能是否具备必要条件。
- 页面显示准备中、执行中、等待授权、已完成、失败或已停止等状态。
- 长任务不会因为一条工具调用返回就被误认为结束。
- 用户可以停止任务；不因为关闭页面就把“用户主动停止”和“页面断开”混为一谈。
- 未授权访问或操作会被拒绝，不能靠修改技能说明获得更多权限。

### 4.3 使用后

- 用户拿到真实可下载的文件，并能分辨不同版本。
- 成功、部分完成、失败和停止应明确区分；不展示误导性的完成状态。
- 结果可以继续修改，或者下载后交付给同事。
- 失败时告诉用户是输入问题、缺少工具、权限不足、资源不足还是平台暂时不可用，并给出下一步。

以上状态和用户文案是业务要求，具体页面方案由产品设计在对应阶段落实；本轮不增加完整远程桌面或开发工具界面。

### 4.4 文件与工具的保留规则

- 同一会话中的工作文件不与其他用户或其他会话混用。
- M5 验收完成后，会话文件默认在最后使用后保留七天。
- 七天不代表任务会连续运行七天，也不代表程序会在后台一直工作。
- 空闲三十分钟后可停止占用计算资源，用户回来时恢复文件并重新执行需要的步骤。
- 到期文件不是永久档案，重要成果应下载或按企业文件政策另行保存。
- 工具模板可以长期复用，但不得夹带客户业务文件。
- 修改模板主要影响新会话；已有会话应用新配置需要明确重建，不能悄悄改变正在使用的环境。

界面和帮助文档应告知保留期、恢复限制以及删除后是否仍处于备份保留期。完整数据删除不能仅以页面上“看不见了”作为验收。

## 5. 本地、托管云与自建虚拟机的业务选择

| 运行方式 | 适合的情况 | 业务优势 | 需要承担的事项 | 推进顺序 |
|---|---|---|---|---|
| 本地部署 | 已有自有服务器，希望控制工作文件运行位置 | 可与企业现有部署结合，不依赖外部运行服务 | 容量准备、运行维护、备份与资源限制 | 第一批 |
| 托管云环境 | 希望快速获得线上运行能力，允许使用批准的外部服务 | 减少自建运行基础设施的前置工作 | 供应商费用、地区可用性、数据授权和服务依赖 | 第一批 |
| 自建虚拟机 | 需要自主控制虚拟机运行环境和长期运维策略 | 可控制运行基础设施，并复用已完成的业务体验 | 更高的部署、硬件、容量和运维要求 | 后续阶段 |

普通使用者应面对统一的任务体验，而不是为不同运行方式重学技能。运行方式由组织配置和授权决定，不能交给模型随意切换。

### 必须说清的两个问题

**“本地”不等于直接在每位用户的桌面电脑上运行。** 本轮指 ZGI 部署方控制的服务器运行环境；桌面用户通过控制台使用。

**“本地运行”不等于所有数据一定不离开企业。** 模型服务、文件存储、联网访问等仍需单独核对。如果客户要求数据不外流，必须把这些环节一起纳入部署和权限检查，不能只看脚本在哪里执行。

托管云会接触任务所需的代码、输入文件和工作内容。启用前必须确认组织授权、数据分类和供应商使用条件；本地不可用时不能自动把资料转移到云端。

本方案不预设哪种方式一定更便宜。应按真实任务量、资源占用和维护投入比较。

## 6. 分阶段交付：每一步业务上能得到什么

“MVP”在本文指：能够解决一个明确问题、可以演示且可以验收的最小可用成果。它不等于面向所有客户正式开放。

| 阶段 | 业务交付 | 谁能使用 | 如何验收 | 暂时不能承诺 |
|---|---|---|---|---|
| M0：建立现状基线 | 明确旧功能能完成的工作、已知失败和试点任务 | 产品、测试、试点业务代表 | 同一批样本重复执行，结果和失败记录可对比 | 尚未提供新工作能力 |
| M1：建立可靠管理 | 内部可以跟踪任务和资源，异常不会无记录地遗留 | 内部研发和测试 | 模拟故障后任务可定位、可停止、可清理 | 尚不是用户可见版本 |
| M2：本地任务执行 | 本地处理文件、查看进度、停止任务并取得成果 | 内部测试人员 | 真实文件结果正确；停止后任务确实终止 | 尚未完成自然语言 Agent 的完整入口 |
| M3：托管云执行 | 同一任务可在本地与托管云分别完成 | 内部测试人员 | 两种方式均通过相同核心任务和异常场景 | 暂不宣传完整七天文件保留 |
| M4：首个用户可用版本 | 用户在控制台交付文件、让 Agent 连续处理并下载结果 | 白名单试点用户 | 完成销售汇总及追加修改；旧技能不受影响 | 仍以已准备工具、离线任务为主 |
| M5：文件保留与工具模板 | 用户在保留期内继续工作，团队复用准备好的工具 | 扩大的试点用户、技能维护者 | 释放计算或平台重启后可恢复文件；模板不含业务资料 | 文件恢复不等于所有后台程序继续运行 |
| M6A：受控联网 | 从批准来源获取信息 | 获授权的试点用户 | 允许的来源可用；不允许的来源确实被拒绝 | 不是无限制上网 |
| M6B：扩展技能工具 | 更多需要额外软件包的自定义技能可以接入 | 技能开发者和管理员 | 缺少工具时可准备、失败可解释、准备后可复用 | 不是所有软件均可随意安装 |
| M6C：联动平台业务 | 脚本使用已授权的模型或业务工具 | 获授权的业务团队 | 未授权调用被拒绝；需审批的动作不能绕过审批 | 不自动获得生产系统写权限 |
| M7：自建虚拟机 | 企业可在自有虚拟机环境运行同一类任务 | 有自建条件的客户 | 同一技能和任务可复现，部署位置与授权一致 | 不提供无感跨环境迁移 |
| M8：正式运营 | 具备预算、用量、支持、恢复和逐步开放机制 | 经正式准入的组织 | 故障演练、旧业务回归、费用核对和支持流程通过 | 仍受任务范围与资源额度约束 |

### 交付门槛

每个阶段必须同时具备：

- 用户或内部验收人员能复现的演示。
- 正常、失败、停止和权限拒绝的结果记录。
- 相同任务与上一版本的对比。
- 清晰的使用限制及支持说明。
- 可停止开放新能力的退回方案。

如果新功能演示通过，但旧功能变差、文件无法取得或费用失控，该阶段不能算通过。

## 7. 如何判断升级真的带来了业务价值

### 7.1 指标口径

先在 M0 测量基线，再以同一批任务持续对比。下面是建议记录的指标，不是已经达到的成绩，也不是尚未测量就对外承诺的目标。

| 指标 | 业务含义 | 计算与核对方式 |
|---|---|---|
| 任务交付成功率 | 用户是否真正拿到了符合要求的结果 | 正确且可获取的成果数 ÷ 约定试点任务数；部分完成单独记录 |
| 结果正确性 | 文件内容是否满足业务规则 | 样本预期值、记录数、金额和格式核对；必要时人工复核 |
| 完成时间 | 用户从提交到拿到成果等了多久 | 包含准备、排队、执行与审批时间，不只看脚本运行时间 |
| 人工介入率 | 有多少任务仍需要研发或客服协助 | 需要额外人工排障或搬运文件的任务比例 |
| 技能接入时间 | 从提交技能到首次成功执行需要多久 | 分开记录材料准备、审核、工具准备和适配工作 |
| 文件取得成功率 | 页面显示的成果能否实际下载使用 | 核对下载可用性、内容与任务对应关系 |
| 继续工作成功率 | 用户回来后能否继续原任务 | 在规定保留期内恢复文件并完成追加任务的比例 |
| 单次成功交付成本 | 花费是否与成果匹配 | 同期任务总消耗 ÷ 成功交付数，包含失败与重试消耗 |
| 试点复用情况 | 用户是否持续使用而非仅试用一次 | 周期内再次完成任务的团队或用户比例 |

统计必须区分输入错误、权限拒绝、工具缺失、模型处理错误和平台故障。被拒绝的任务单独展示，不能简单删除后只呈现一个好看的成功率。

### 7.2 业务验收方法

采用四组任务：

1. **正常任务**：多文件处理、生成下载文件、追加修改。
2. **需要澄清的任务**：字段缺失、规则冲突、输入损坏，检查是否询问用户或给出明确错误。
3. **用户控制任务**：中途停止、重新执行、退出页面后查看状态、保留期内回来继续处理。
4. **边界任务**：无权限的数据、未批准的网络来源、超过额度的工作，检查是否正确拒绝。

固定样本必须可以重复使用。平台稳定性的自动化验证与模型业务结果的验证分开记录，不能把随机模型结果全部归因为运行环境。

### 7.3 放量条件

具体量化目标在 M0 基线与试点任务确定后冻结，避免在不了解现状时凭空承诺。

但以下条件不因阶段或样本规模而放宽：

- 用户之间不能看到对方的工作文件。
- 关闭新能力后旧业务仍可使用。
- 下载内容必须真实对应任务结果。
- 任务停止和权限撤销必须生效。
- 文件保留与数据运行位置不得误导用户。
- 尚未通过验证的能力不得包装成已上线承诺。

## 8. 成本、风险与运营规则

### 8.1 成本要如何看

本轮成本由两部分组成：一次性的建设投入，以及持续的使用与运营投入。

持续成本包括：模型调用、运行资源、文件保存、网络传输、工具准备、故障重试、供应商服务、人员维护和客户支持。

比较本地与托管云时，应统计完成同一项工作的总成本，不能只比较某台服务器的价格或一次调用费用。本文不引用未验证的供应商价格，也不据此设计具体收费方案。

建议先完成成本计量，再决定按使用量、套餐还是企业额度提供服务。计量能力交付不等于收费规则已经获批。

### 8.2 初始业务规则

- 按组织控制可同时运行的工作数量、可用工具、联网范围和存储额度。
- 超出额度时提示排队、减少输入或申请增加额度，不能无限制消耗。
- 文件保留期与计算运行时间分开显示。
- 空闲时停止占用计算资源，但继续工作可能需要等待环境恢复。
- 超出预算时停止接受新的计算任务，不以删除已保存成果作为省钱手段。
- 客户可以停用新能力；停用不能阻止其取回尚在保留期内的文件。

具体底层资源规格由技术方案管理，业务端以可理解的任务额度、文件限制和预算提示呈现。

### 8.3 风险与处理方式

| 风险 | 业务后果 | 管理措施 |
|---|---|---|
| AI 输出不正确 | 错误成果被当成正式结论 | 固定规则核对、显示失败或部分完成，高影响用途保留人工复核 |
| 数据误入不允许的云环境 | 违反客户的数据使用要求 | 组织提前授权，明确运行位置，禁止静默转云 |
| 文件丢失或保留期误解 | 用户无法继续工作或交付成果 | 七天保留验收后再宣传，说明到期规则，提供下载与恢复指引 |
| 自定义技能过度承诺兼容 | 客户导入后发现无法使用 | 展示所需工具、权限和限制，维护实际通过的技能样例 |
| 未授权业务操作 | 对生产系统造成影响 | 平台权限与审批保持有效，不因脚本调用而绕过 |
| 供应商或自有环境不可用 | 任务中断、延迟与客服压力 | 明确暂时不可用、恢复或重试状态，不重复触发危险业务动作 |
| 费用持续增长 | 单位交付成本不可接受 | 空闲释放资源、组织额度、预算限制、失败与重试分析 |
| 为追求自由度影响旧业务 | 老客户稳定性下降 | 默认关闭新能力，旧路径保留，各阶段重复验证旧任务 |

### 8.4 支持与运营交付

正式开放前至少准备：

- 用户快速入门、支持的任务类型和限制说明。
- Skill 开发者工具准备及接入指南。
- 管理员授权、运行位置、文件保留和预算说明。
- 失败原因及“用户自助、客服处理、研发升级”分流说明。
- 异常暂停、文件取回和恢复的演练记录。
- 对外发布说明，准确区分试点、正式可用和后续计划。

## 9. 推进节奏、组织分工与决策点

### 9.1 时间预期

时间沿用技术方案，基于两名后端、一名平台工程师，产品、前端、测试阶段性投入。

- 首个用户可见的本地与托管云版本：约 **8–12 周**。
- 包含文件保留、工具扩展、自建虚拟机和正式运营的完整方案：约 **18–26 周**。
- 技术方案估算建设投入约 **55–80 人周**，不是合同承诺；M0 核验后更新。

这些时间不意味着第八周已经开放全部软件安装、联网和企业系统调用。M4 是首个可用版本，M5、M6、M7 分别交付更长期的使用价值。

### 9.2 职责

| 角色 | 主要责任 |
|---|---|
| 业务负责人 | 选择有实际价值的试点任务，确认成果能否用于工作 |
| 产品负责人 | 使用流程、权限与限制表达、阶段范围和对外承诺 |
| 技术与平台负责人 | 可执行性、稳定性、隔离、恢复和运行成本 |
| Skill 开发者 | 技能说明、必要工具、业务规则和样例输入输出 |
| 测试负责人 | 固定样本、结果核对、失败场景和旧业务验证 |
| 客户成功与运营 | 试点反馈、用户培训、问题分流和用量分析 |
| 组织管理员 | 客户侧授权、运行位置、预算和数据使用规则 |

### 9.3 三个业务决策点

**第一个决策点：M0 结束。** 确认试点对象、核心任务、样本与指标基线，决定是否投入后续建设。

**第二个决策点：M4 结束。** 观察真实交付、人工介入与成本，决定扩大试点、优先补齐哪类工具，或者暂缓扩展。

**第三个决策点：M8 放量前。** 确认费用、支持、数据规则和故障恢复成熟，决定正式开放范围与业务额度。

如果阶段收益不足，可以暂停扩大投入。已交付的可用能力仍应保持完整，不能要求用户等到整个项目结束才拿到结果。

### 9.4 每周业务评审

每周用同一组问题评审：

1. 本周新增了什么用户可完成的工作？
2. 哪些任务确实交付了结果，哪些仍失败？
3. 与原来相比，少了哪些人工步骤？
4. 是否出现新的数据、权限、成本或旧业务问题？
5. 下一阶段是否具备进入条件？

技术完成度是输入，业务可用成果才是阶段判断依据。

## 10. 对外承诺边界与最终验收

### 可以作为目标说明的内容

- 帮助用户在受控环境内完成脚本与文件型工作。
- 支持企业自有部署与批准的托管云选择，并逐步支持自建虚拟机。
- 减少普通带脚本技能的专用适配工作。
- 提供真实文件成果、任务状态、停止与恢复能力。
- 逐步扩大工具与业务协作能力，同时维持权限和费用控制。

实际对外宣称某项能力已可用，必须以对应阶段验收为前提。

### 不能承诺的内容

- 所有技能和所有软件导入后都能直接运行。
- AI 输出无需人工核对，或可以自动完成所有高风险业务动作。
- 能随意访问外部服务器、企业内网和生产数据库。
- 开启本地运行就自动满足所有数据保密或合规要求。
- 工作文件永不丢失、永不过期，或任务永久在后台执行。
- 在不同运行方式之间任意无感切换，且不需要确认数据流向。
- 当前时间估算等同已经确定的正式发布日期。

### 最终业务验收

完整方案交付时，业务负责人应能确认：

1. 普通用户不必操作底层环境，就能完成约定的文件任务并拿走成果。
2. 用户能在同一会话继续修改，在规定保留期内恢复工作文件。
3. 开发者更容易接入普通脚本技能，缺少工具时有明确处理路径。
4. 本地、托管云、自建虚拟机使用同一类业务任务验证，结果口径一致。
5. 管理员能够决定谁能用、在哪里运行、允许做什么以及可使用多少资源。
6. 权限不足、任务失败、用户停止和平台异常都不会被伪装成成功。
7. 旧客户的现有功能不因新能力而被强制改变。
8. 运营能够解释费用、支持用户取回成果，并执行异常处理与暂停开放。

本项目的业务价值，不是“多了一台虚拟机”，而是让更多工作能够在 ZGI 内完成、交付和复用，并且让企业能够管理这项能力。
