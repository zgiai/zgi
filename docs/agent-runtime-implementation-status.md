# Agent Runtime Implementation Status

This document records verified delivery evidence for the Agent execution environment roadmap. A stage is complete only when its stated evidence is available. Planned commands or capabilities are not recorded as passing results.

## Operating contract

Deliver the staged Agent execution environment on the dedicated `px/agent-runtime-execution-environment` branch, verified by the stage-specific automated tests, real backend exercises, and cleanup evidence, while preserving the existing one-shot Script Skill behavior, dependency authorization, Runtime Workspace external-access boundary, and public response contracts. The original `px/runtime-workspace-integration` branch remains separate.

Work only in the dedicated execution-environment worktree. At each iteration, run the narrowest relevant test first, record the result here, then broaden validation. If a required real backend, credential, or Linux capability is unavailable, mark that evidence as blocked instead of substituting a mock result.

## Baseline

- Branch: `px/agent-runtime-execution-environment`
- Baseline commit: `b7c4734bf`
- Required Go toolchain: `1.26.2`
- Local developer shell observed before M0: Windows with Go `1.25.0`
- Existing runtime execution: one-shot Sandbox plus synchronous command and Skill execution
- Existing reusable behavior: Python and Node Script Skills, file inputs, Artifact persistence, bundled local package recognition, dependency Profiles, dependency authorization, and dependency-scan configuration
- Existing `runtimeworkspace` domain: external Agent exposure and authentication; it is not a filesystem execution environment and must not authorize Agent Runtime APIs

## M5A checkpoint progress

The opt-in Worker checkpoint path serializes regular Workspace files and directories through the authenticated Runtime Agent, publishes a bounded archive and checksum manifest to a private Worker volume, and stores the committed key on the Binding. A pending key survives a control-plane restart during suspension. On `ErrNotFound` from the old compute allocation, resume creates a replacement from the same approved Profile and imports the archive; a failed import destroys the replacement. PostgreSQL Job admission now locks the active Binding generation, so a Job cannot be inserted after suspension wins the state transition. A suspension waits for already queued/running Jobs to finish.

The initial validation covered focused Linux Go tests for `agentexecution`, `runtimeagent`, `workspacecheckpoint`, `localruntime`, `hostedruntime/e2b`, and `cmd/agentworker`; PostgreSQL migration and Job repository tests against a disposable PostgreSQL 16 container; a Runtime Agent → file store → restart → new Runtime Agent file/download round trip; `go vet`; and `go test -race` for the checkpoint packages. The setting remains off by default.

The first real M5A run on 2026-09-30 exposed an E2B traffic-proxy limitation: HTTP trailers did not reach the Worker, so an otherwise successful archive was rejected. The archive protocol now carries a version marker and SHA-256 checksum in the body, and regression tests cover trailer-stripping, truncation, and corruption. A rebuilt E2B template then passed the real account contract, including two-CSV aggregation, archive export, pause/resume, forced deletion of the original Sandbox, replacement creation, archive import, and byte-exact result download. The provider listed no remaining Sandboxes after the run. The native gVisor replacement-workspace and full backend contract tests also passed on the dedicated Linux node, using an image preloaded into the Worker containerd namespace. These are backend gates, not yet a full Worker/DB/UI checkpoint lifecycle or cross-node retention acceptance.

An opt-in S3-compatible checkpoint store now provides immutable conditional object writes, SHA-256 verification, and shared access from separate Worker processes. A disposable SeaweedFS S3 server passed save/open/retry/delete tests using two independent store clients; the in-memory HTTP test covers conflicting writes and corruption. This validates the object data path, not yet the complete Worker/DB/UI recovery or seven-day retention semantics.

The next M5 increment adds a persisted retention deadline separate from the 30-minute compute-idle deadline. A Worker with checkpoint storage enabled reaps suspended Bindings after seven days since last use, deleting the archive and rejecting expired resumes. Generation fencing prevents a stale reaper from deleting a concurrently resumed session. The migration and repository query passed against a disposable PostgreSQL 16 container; the service and reaper unit tests cover early/late cleanup and concurrency. Home Snapshot and end-to-end crash-recovery gates remain open.

Checkpoint replacement now commits the new Binding reference and a cleanup task for the old object in one PostgreSQL transaction. The cleanup loop removes superseded objects with a claim lease and retry; deleting a Binding waits for checkpoint removal before recording `deleted`. A failed delete remains `deleting` and is retried by the retention loop. PostgreSQL and reconciler tests cover these boundaries. This does not yet address an opaque provider allocation created immediately before the Worker process crashes, or demonstrate a complete Worker/DB/UI restart exercise.

The E2B allocation path now records a delayed reconciliation task before calling the provider. Every created Sandbox carries the attempt ID in provider metadata. Once the bounded creation/import window has elapsed, the cleanup worker lists running and paused Sandboxes with that metadata, preserves the Sandbox referenced by an active Binding, and deletes unrecorded attempts. The task is leased and retried on provider errors. Fake-provider crash-window tests and E2B paginated-list contract tests pass; a real-provider crash injection is still required before this gate is closed.

The allocation task now also records the Binding generation. If a Worker disappears during initial allocation, a matching still-`allocating` Binding becomes `failed` after orphan cleanup so the API can replace it. If restoration disappears mid-flight, a matching still-`resuming` Binding returns to `suspended` with its checkpoint intact so the next request can retry. A task from an older generation cannot demote a newer Binding. This is delayed crash recovery, not an instantaneous failover guarantee; PostgreSQL and unit tests pass, while a live provider crash injection remains open.

An operator-approved Home Snapshot can now be selected in the console Agent configuration. The API publication allowlist and Worker's PostgreSQL row independently verify organization, Profile, backend, and approved status. The immutable prebuilt image digest or E2B template ID is pinned on the Binding and reused after recovery. PostgreSQL migration tests enforce that an approved artifact cannot be rewritten; local and E2B adapter tests verify the selected artifact. The immutable base-template path is separate from the checkpointed session home; an explicit in-place template-switch rebuild and live dual-backend/UI acceptance remain open.

A database-level reference guard now rejects new Bindings with missing or cross-organization approved templates and blocks template-row deletion while a live Binding references it. PostgreSQL migration tests cover rejection and release after the Binding is deleted. The API's published-Agent references are in a different database, so operator retirement still needs that separate check.

Idempotent `CreateBinding` now retrieves an existing owner-scoped Binding before checking the current template approval row. Revoking approval for new sessions therefore does not strand a session already pinned to that immutable artifact; a different idempotency key still fails the approval check. Repository and service tests cover the owner boundary and this continuation behavior.

The authenticated Worker now exposes an owner-scoped lookup by Binding idempotency key. If a console Agent's draft Profile or Home Snapshot changes, the API keeps an existing conversation on its original Binding after an idempotency conflict instead of failing the next turn or silently switching templates. A newly created conversation still receives the newly approved configuration. HTTP and API gateway tests cover the lookup and cross-organization denial. This is continuity, not the separate explicit template-switch rebuild operation.

The M5 operator guide and console configuration now describe the explicit new-conversation handoff for a template change: export required files from the old conversation, publish the new approved template, start a new conversation, verify its tool, and re-upload files. Existing sessions remain pinned. This is not an automatic or in-place rebuild, which remains beyond the current implementation.

## Compatibility gates

Every later stage must continue to verify:

- Existing Agents do not receive Shell or Workspace tools when the new configuration is absent or disabled.
- Runtime Workspace credentials cannot call Agent Runtime endpoints.
- Existing Script Skills retain input, dependency, output, Artifact, stderr, non-zero exit, and package-size behavior.
- Frontend disconnect is not treated as a user stop request.
- Model-visible tool output, persisted transcript content, audit summaries, and raw Job logs obey separate size and redaction rules.
- Disabling new Binding creation does not prevent authorized users from retrieving retained files or operators from cleaning resources.
