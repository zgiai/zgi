# Agent API

Use this API to call the latest published version of the current Agent from an external system.
The API is streaming-only and runs under the Agent API Key that is bound to this Agent.

## Integration Overview

<div>
  ### Base URL

<CodeGroup title="Code">

```text
{apibase}
```

</CodeGroup>

### Authentication

Send the Agent API Key from your server. `Authorization: Bearer` is preferred and takes precedence over `X-API-Key` when both are present.

<CodeGroup title="Headers" targetCode={`Authorization: Bearer {api_key}\nX-API-Key: {api_key}`}>

```text
Authorization: Bearer {API_KEY}
X-API-Key: {API_KEY}
```

</CodeGroup>

Keep API Keys on your server side. Do not expose them in browser code or public clients.

For every stateful Agent operation, your trusted server must also send `X-External-User-ID`. Derive one stable, opaque id (1–128 Unicode characters, case-sensitive) from the authenticated application user. Do not use an email address, phone number, or other PII. ZGI stores only a workspace-and-Agent-scoped derived UUID, and uses it to isolate conversations, stream recovery, continuations, files, and Agent Memory.

### Minimum landing-page flow

1. Call `GET /agents/config` on your server to load the title, opening statement, theme, suggested questions, file capability, and memory flags.
2. If the user selects a file, call `POST /files/upload`, then include the returned file id in the chat request's `file_ids`.
3. Call `POST /agents/chat` through your own server-side proxy. Save `conversation_id`, `message_id`, and the latest SSE `id`.
4. Restore history through the conversation and message APIs; reconnect through events and cancel through stop.
5. Route the two public pause types: workflow approval/question and Skill user input. Each resumes the same message through its own continuation endpoint.

Normal Agent JSON success responses use `{ "code": "0", "message": "success", "data": ... }`. Errors use `{ "code": "...", "message": "..." }` with the matching HTTP `4xx/5xx` status. File upload and the legacy-compatible `/info` and `/parameters` success responses return objects directly; successful streaming endpoints return `text/event-stream` directly.

    ### Streaming Format

    Agent streams use native SSE event names. The `data` line also contains a JSON envelope with the same `event` name.

    <CodeGroup title="SSE Format">
    ```text {{ title: 'SSE' }}
    id: 1715750400000-0
    event: message
    data: {"event":"message","data":{"conversation_id":"...","message_id":"...","answer":"Hello"}}
    ```
    </CodeGroup>

    Dispatch by the native `event:` value or by the JSON `event` field. For response text, concatenate `message.data.answer` by `message_id`. Recoverable `message` and progress events include an SSE `id`; keep the latest id for reconnects.

    ### Event Handling

    Chat, stream recovery, and both continuation endpoints share the same Agent SSE contract. A minimum implementation handles `message_start`, `message`, `message_retract`, `message_end`, and `error`, and persists the latest non-empty SSE `id`. Add the matching request event when supporting Skill user input or workflow pauses.

    See “Agent Event Integration Guide” below for each event's purpose, trigger, client action, payload shape, and integration example. Ignore unknown events and unknown payload fields for forward compatibility.

    ### Errors

    - `400`: invalid request body, invalid ids, non-streaming `response_mode`, missing/invalid `X-External-User-ID`, or a mismatch with legacy `user`
    - `401`: missing, invalid, inactive, expired, or revoked API Key
    - `404`: Agent has no published version or cannot be found
    - `500`: internal service error

<Row>
  <Col>
    Use this endpoint when the client disconnects while an Agent message is still running.

    ### Path and Headers

    <Properties>
      <Property name='conversation_id' type='uuid' propKey='conversation_id'>Required conversation id returned by chat.</Property>
      <Property name='Authorization' type='string' propKey='Authorization'>Required Agent API Key.</Property>
      <Property name='X-External-User-ID' type='string' propKey='X-External-User-ID'>Required original conversation owner; a different user cannot replay the stream.</Property>
    </Properties>

    ### Query Parameters

    <Properties>
      <Property name='message_id' type='string' propKey='message_id'>
        Required. The assistant `message_id` returned by `message_start`.
      </Property>
      <Property name='after_id' type='string' propKey='after_id'>
        Optional. Last SSE `id` received by your client. Omit it to replay from the beginning of the recoverable stream.
      </Property>
    </Properties>

    The event store is short-lived. Current runtime stores Agent stream events for 24 hours. If the stream is still active but the event store is unavailable or expired, the server emits `error` with `message: "stream events expired"`.

    ### `200` Response

    `text/event-stream` containing persisted events after `after_id`, in order. It uses the same native event names, JSON envelopes, and event field definitions as Send Chat Message. The endpoint stays connected while the message is active and ends after the terminal event. It does not create a new message.

    ### Recovery Flow

    - Save `conversation_id`, `message_id`, and the latest SSE `id` from every Agent event that includes `id:`.
    - On reconnect, call this endpoint with the same API Key and `X-External-User-ID`.
    - Resume from `after_id`. De-duplicate events by SSE `id` if your client may retry.
    - If an event has no SSE `id`, treat it as a non-recoverable fallback event and do not use it as `after_id`.
    - Stop listening after `message_end` with `completed`, `stopped`, `error`, or `failed`, or after an `error` event.

    ### Page reload and in-page reconnect are different

    During an in-page network interruption, the client still owns the rendered text. Resume incrementally with the latest `after_id` and deduplicate by SSE `id`. After a page or application restart, do not trust a local cursor by itself: load message history first, then replay the newest running or waiting message from the event-stream beginning without `after_id`.

| Current state | Detection | Recovery action |
| --- | --- | --- |
| Running | `runtime_status=running` with `active_message_id` | Replay from the beginning and keep the connection open; use the newest `after_id` for later in-page reconnects |
| Waiting for approval | Latest message has `status=waiting_approval` | Replay that message to rebuild `approval_requested`; message metadata may provide an immediate form fallback |
| Waiting for workflow answer | `question_answer_requested`, or `user_input_requested.source=agent_workflow_question_answer` | Render the question/choices and call workflow continuation |
| Waiting for Skill input | Any other `user_input_requested` | Key answers by question id and call user-input continuation |
| Waiting for token budget | Latest message has `status=waiting_budget` | Render the independent budget actions and call token-budget continuation with the matching `request_id` |
| Completed or failed | `completed`, `stopped`, `error`, or `failed` | Render history only; do not open a recovery stream |

    Waiting conversations are normally no longer `running`, so checking only `active_message_id` is insufficient. Inspect the newest message status and recover that same `message_id`. If retained events and message metadata cannot reconstruct the form, actions, or request id, show an unrecoverable-state UI instead of inventing approval actions.

    ### Automatic reconnect rules

    Keep the last completely processed SSE id, de-duplicate every replayed id, and retry network failures, `429`, and retryable `5xx` responses with bounded exponential backoff. Do not retry `400/401/403/404`. Abort both the reader and pending delay when the user navigates away. Never repeat an uncertain chat POST; once conversation/message ids exist, switch to the events endpoint.

    ```ts
    async function reconnectStream({ conversationId, messageId, lastEventId, signal }) {
      const seen = new Set<string>();
      let cursor = lastEventId;

      for (let attempt = 0; attempt <= 5; attempt += 1) {
        const query = new URLSearchParams({ message_id: messageId });
        if (cursor) query.set('after_id', cursor);
        const response = await fetch(
          `/api/v1/agents/conversations/${conversationId}/events?${query}`,
          { headers: agentHeaders, signal },
        );
        if ([400, 401, 403, 404].includes(response.status)) throw new Error('not retryable');
        if (!response.ok && response.status !== 429 && response.status < 500) throw new Error('not retryable');

        let terminal = false;
        try {
          await consumeSSE(response, (event) => {
            if (event.id && seen.has(event.id)) return;
            if (event.id) {
              seen.add(event.id);
              cursor = event.id;
            }
            renderAgentEvent(event);
            terminal = event.event === 'message_end' || event.event === 'error';
          });
          if (terminal) return;
        } catch (error) {
          if (signal.aborted) throw error;
        }
        if (attempt === 5) throw new Error('automatic recovery exhausted');
        await delay(Math.min(800 * 2 ** attempt, 8000), signal);
      }
    }
    ```

    ### Rendering approval UI

    Treat `approval_requested` as the live source of truth. Its credential is the top-level `approval_token`; display content, fields, actions, and expiration are nested under `approval_form`. Do not mistakenly read them from `data.actions`, `data.fields`, or `data.expires_at`.

    ```text
    event: approval_requested
    data: {"event":"approval_requested","data":{"conversation_id":"f1f7503a-9e28-4af5-9d6d-9e23fb5a8994","message_id":"d57058bd-50f1-4bc2-931d-e22a739190e6","workflow_run_id":"run-01","approval_form_id":"form-01","approval_token":"{approval_token}","ui_approval_allowed":true,"approval_form":{"id":"form-01","node_id":"approval-node","node_title":"Human review","content":"Review the information and submit a decision.","fields":[],"actions":[{"id":"approve","label":"Approve"},{"id":"reject","label":"Reject","style":"danger"}],"submit_methods":{"webapp":{"enabled":true}},"expiration_at":1789002351,"token":"{approval_token}"}}}
    ```

    Normalize the live event into one approval UI model. On page reload, pass `metadata.agent_workflow_continuation` as the envelope and `metadata.workflow_runs[].approval.approval_form` as the form to the same normalizer, so live handling and durable recovery cannot drift to different field paths.

    ```tsx
    function approvalFromEvent(event) {
      const data = event.data;
      const form = data.approval_form ?? {};
      return {
        ...form,
        form_id: data.approval_form_id ?? form.id,
        token: data.approval_token ?? form.token,
        ui_allowed: data.ui_approval_allowed !== false,
      };
    }

    function ApprovalCard({ approval, submit }) {
      const [inputs, setInputs] = useState({});
      const expired = toTime(approval.expiration_at) <= Date.now();
      if (!approval.ui_allowed) return <OutOfBandApprovalNotice />;
      return <section>
        <h3>{approval.node_title || 'Approval required'}</h3>
        <p>{renderSafeContent(approval.content)}</p>
        {approval.fields?.map(field => (
          <Field key={field.id || field.key || field.name}
            definition={field}
            onChange={value => setInputs(current => ({
              ...current,
              [field.id || field.key || field.name]: value,
            }))} />
        ))}
        {approval.actions?.map(action => (
          <button key={action.id} disabled={expired}
            onClick={() => submit({
              type: 'approval',
              approval_token: approval.token,
              action: action.id,
              inputs,
            })}>
            {action.label || action.id}
          </button>
        ))}
      </section>;
    }
    ```

    Render `content` only as safe text or structured data, and render only the actions returned in `approval_form.actions`. Enable the controls as soon as the matching `message_end.status=waiting_approval` arrives; do not wait for the HTTP response body to close. Disable all actions after `approval_form.expiration_at`, after `approval_expired`, or while the continuation request is in flight.

    When `ui_approval_allowed=false`, the API redacts both the top-level `approval_token` and the form `token`. Direct the user to the workflow's configured approval channel instead of constructing an API request. On page reload, the latest message metadata can provide `workflow_runs[].approval.approval_form` as a temporary snapshot while the event stream is replayed. If neither the retained events nor metadata contain a token and advertised actions, show an unrecoverable-state prompt rather than constructing a request.

    ### Distinguishing workflow questions from Skill input

    A workflow question can emit `question_answer_requested` and then a projected `user_input_requested`. When the projected event has `source=agent_workflow_question_answer`, it still uses this workflow continuation endpoint. Only other `user_input_requested` events use the Skill user-input continuation endpoint.

    ```ts
    const workflowQuestion = event.event === 'question_answer_requested'
      || (event.event === 'user_input_requested'
        && event.data.source === 'agent_workflow_question_answer');
    ```

## Agent Event Integration Guide

Artifacts with `access_mode: authenticated` omit `url` and `download_url`. Fetch
their bytes through the conversation file endpoint using the same API key and
external-user identity. Never construct a public ToolFile URL from `file_id`.

This section defines the SSE contract shared by chat, stream recovery, and continuation endpoints. Dispatch on the native `event:` field first, then read the event payload from `data.data` in the JSON envelope. Do not parse the whole response as one JSON document or wait for the connection to close before rendering.

### Common Envelope and Recovery Fields

<Properties>
  <Property name="id" type="string?" propKey="SSE id">
    The SSE transport id outside the JSON envelope. Persist every non-empty value as `lastEventID`;
    after a disconnect, pass it as `after_id` to the events endpoint. Initial or fallback events may
    not have an id.
  </Property>
  <Property name="event" type="AgentEventName" propKey="SSE event">
    The native SSE event name and the discriminator your client should switch on.
  </Property>
  <Property name="data.event" type="AgentEventName" propKey="event">
    The event name repeated inside the JSON envelope. It should match the native `event:` field.
  </Property>
  <Property name="data.data" type="object" propKey="data">
    The event payload. Every “Key fields” column below describes fields inside this object.
  </Property>
  <Property name="conversation_id" type="uuid" propKey="conversation_id">
    The conversation that owns the event. Use it when updating local state and calling recovery,
    stop, or continuation endpoints.
  </Property>
  <Property name="message_id" type="uuid" propKey="message_id">

    waiting state by this id.
  </Property>
  <Property name="event_id / sequence" type="string? / integer?" propKey="event_id">

  </Property>
  <Property name="created_at / created_at_ms" type="integer?" propKey="created_at">

    deduplication keys.
  </Property>
  <Property name="usage" type="object" propKey="usage">

    accumulate them per message for real-time usage display.
  </Property>

  </Property>

  </Property>

  </Property>

### Recommended Client State Machine

1. On `message_start`, persist `conversation_id` and `message_id` from the response headers or event.
2. Persist every non-empty SSE `id` immediately and deduplicate by id.
3. Build the visible answer only from `message`, `message_retract`, and `message_end.answer`; never append progress events to the final answer.
4. Treat `completed`, `stopped`, `error`, and `failed` as terminal `message_end.status` values. For `waiting_approval`, `waiting_question`, or `waiting_budget`, keep the same message and call the matching continuation endpoint.
5. After a disconnect, recover from the events endpoint. Do not submit the original chat request again.

<CodeGroup title="TypeScript Event Dispatcher">

```ts
type AgentEvent = { event: string; data: Record<string, unknown> };

function applyAgentEvent(frame: AgentEvent) {
  const data = frame.data;
  switch (frame.event) {
    case 'message_start':
      saveMessageIdentity(String(data.conversation_id), String(data.message_id));
      break;
    case 'message':
      appendAnswer(String(data.message_id), String(data.answer ?? ''));
      break;
    case 'message_retract':
      retractCandidate(String(data.message_id), String(data.presentation_disposition));
      break;
    case 'user_input_requested':
    case 'approval_requested':
    case 'question_answer_requested':
      renderPendingInteraction(frame);
      break;
    case 'token_budget_requested':
      renderTokenBudgetActions(frame);
      break;
    case 'message_end':
      transitionMessage(String(data.message_id), String(data.status));
      break;
    case 'error':
      showSafeError(String(data.message ?? 'Agent execution failed'));
      break;
    default:
      updateOptionalProgress(frame); // Unknown events must be safe to ignore.
  }
}
```

</CodeGroup>

## JSON Errors

Before an SSE stream starts, every endpoint returns errors as JSON with the matching HTTP status. `code` is a stable ZGI error code and `message` is safe to display or log. Validation can add endpoint-specific wording; clients must tolerate additional fields.

<Properties>
  <Property name="code" type="string" propKey="code">
    Machine-readable ZGI error code. Success uses `0`; errors use a nonzero code.
  </Property>
  <Property name="message" type="string" propKey="message">
    Client-safe error description.
  </Property>
</Properties>

<CodeGroup title="Error Response" label="400 JSON">

```json
{
  "code": "199001",
  "message": "Invalid parameter"
}
```

</CodeGroup>

- `400`: malformed JSON, invalid ids or enum values, missing external user, stale Memory revision, or a legacy `user` mismatch.
- `401`: missing, invalid, inactive, expired, or revoked API Key.
- `403`: authenticated caller is not allowed to perform the operation.
- `404`: no published Agent, conversation/message not owned by this user, unknown Memory slot, or expired/already-resolved continuation.
- `409`: conflicting runtime state or optimistic-concurrency conflict when surfaced separately.
- `500`: internal service error. Do not expose upstream/internal details to end users.

## Retry, Security, and CORS

- Use a browser → your BFF/server → ZGI architecture and inject the API Key on the server. Do not send the Key to browser code even when the deployment allows your Origin through CORS.
- Before SSE starts, handle `4xx/5xx` as normal JSON errors. After it starts, handle `error` / `message_end`. Apply exponential backoff only to network errors, `429`, and recoverable `5xx`; do not automatically retry `400/401/403/404`.
- An uncertain retry of the chat POST can create a duplicate message. After `message_start`, prefer recovery through the events endpoint and deduplicate by SSE `id`.
- The machine-readable contract is at `/api/openapi.yaml`; the interactive view is at `/swagger/index.html`.

## Notes

- This API runs the latest published Agent version. Draft configuration is not available.
- An API Key can only access the Agent it is bound to.
- Use `conversation_id` for multi-turn context, `message_id` for stream recovery, both continuation types, and regeneration, and `workflow_run_id` for workflow troubleshooting.
- A complete Next.js server proxy, SSE state machine, and page wiring example is available in the repository at `docs/agent-api-quickstart.md`.
