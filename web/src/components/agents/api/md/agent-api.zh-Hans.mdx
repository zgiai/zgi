# Agent API

使用该接口从外部系统调用当前 Agent 的最新发布版本。
接口只支持流式响应，并使用绑定到该 Agent 的 Agent API Key 鉴权。

## 接入概览

<div>
  ### Base URL

<CodeGroup title="代码">

```text
{apibase}
```

</CodeGroup>

### 鉴权

请在服务端发送 Agent API Key。推荐使用 `Authorization: Bearer`，当同时传入 `Authorization` 和 `X-API-Key` 时，优先使用 `Authorization`。

<CodeGroup title="Headers" targetCode={`Authorization: Bearer {api_key}\nX-API-Key: {api_key}`}>

```text
Authorization: Bearer {API_KEY}
X-API-Key: {API_KEY}
```

</CodeGroup>

请只在服务端保存和使用 API Key，不要暴露在浏览器代码或公开客户端中。

所有有状态 Agent 操作还必须由可信服务端发送 `X-External-User-ID`。请从业务侧已认证用户生成稳定、不透明的 id（1–128 个 Unicode 字符、区分大小写），不要直接使用邮箱、手机号或其他个人信息。ZGI 只持久化按 workspace 和 Agent 派生的 UUID，并用它统一隔离会话、流恢复、各类继续请求、文件和 Agent Memory。

### 复刻落地页的最小调用顺序

1. 服务端调用 `GET /agents/config`，取得标题、开场白、主题色、建议问题、文件和记忆能力开关。
2. 如果用户选择文件，服务端调用 `POST /files/upload`，再把返回的文件 id 放进聊天请求的 `file_ids`。
3. 调用 `POST /agents/chat`，浏览器通过你自己的服务端代理消费 SSE；保存 `conversation_id`、`message_id` 和最新 SSE `id`。
4. 用会话和消息查询接口恢复历史；用 events 接口断线重连，用 stop 接口终止生成。
5. 分流两类公开暂停：工作流审批/问答和 Skill 用户输入；分别通过对应的继续接口恢复同一条消息。

Agent 的普通 JSON 成功响应统一为 `{ "code": "0", "message": "success", "data": ... }`；错误响应统一为 `{ "code": "...", "message": "..." }` 并使用对应的 HTTP `4xx/5xx` 状态。文件上传及旧版兼容的 `/info`、`/parameters` 成功响应是对象本身，SSE 接口成功时直接返回 `text/event-stream`。

    <Properties>

    ### 流式格式

    Agent 使用原生 SSE event 名。`data` 行里也会包含一层 JSON envelope，并带有同名 `event` 字段。

    <CodeGroup title="SSE 格式">
    ```text {{ title: 'SSE' }}
    id: 1715750400000-0
    event: message
    data: {"event":"message","data":{"conversation_id":"...","message_id":"...","answer":"你好"}}
    ```
    </CodeGroup>

    客户端可以按原生 `event:` 分发，也可以解析 JSON 里的 `event` 字段。展示最终回答时，按 `message_id` 拼接 `message.data.answer`。可恢复的 `message` 和进度事件会带 SSE `id`，请保存最新 id 用于重连。

    ### 事件处理

    聊天、断线恢复和两个继续接口使用同一套 Agent SSE 事件契约。最小实现必须处理 `message_start`、`message`、`message_retract`、`message_end` 和 `error`，并保存最新非空 SSE `id`。涉及 Skill 用户输入或工作流暂停时，再处理对应的请求事件。

    每个事件的作用、触发时机、客户端动作、字段结构和接入代码见下方“Agent 事件接入手册”。未知事件和未知字段必须忽略，以保持向前兼容。

    ### 错误

    - `400`：请求体错误、id 非法、`response_mode` 不是 `streaming`、缺少/非法的 `X-External-User-ID`，或与旧 `user` 不一致
    - `401`：API Key 缺失、错误、已停用、已过期或已撤销
    - `404`：Agent 不存在，或没有发布版本
    - `500`：服务内部错误

<Heading
  url="/api/v1/agents/conversations/{conversation_id}/events"
  method="GET"
  title="恢复 Agent 流"
  name="#Recover-Agent-Stream"
/>

<Row>
  <Col>
    当客户端在 Agent 消息仍在运行时断开连接，可以使用该接口恢复流。

    ### 路径参数与请求头

    <Properties>
      <Property name='conversation_id' type='uuid' propKey='conversation_id'>必填，聊天接口返回的会话 id。</Property>
      <Property name='Authorization' type='string' propKey='Authorization'>必填 Agent API Key。</Property>
      <Property name='X-External-User-ID' type='string' propKey='X-External-User-ID'>必填，必须是原会话所有者；其他用户不能回放该流。</Property>
    </Properties>

    ### Query 参数

    <Properties>
      <Property name='message_id' type='string' propKey='message_id'>
        必填。`message_start` 返回的助手 `message_id`。
      </Property>
      <Property name='after_id' type='string' propKey='after_id'>
        可选。客户端最后收到的 SSE `id`。不传则从可恢复流的开头回放。
      </Property>
    </Properties>

    事件存储是短期的。当前 Agent stream events 保存 24 小时。如果消息仍在运行，但事件存储不可用或已过期，服务端会发送 `error`，其中 `message` 为 `stream events expired`。

    ### `200` 响应

    返回 `text/event-stream`，按顺序发送 `after_id` 之后持久化的事件。事件名、JSON envelope 和字段定义与聊天接口完全一致。消息仍在执行时连接会继续等待，并在终态事件后结束；该接口不会创建新消息。

    ### 恢复流程

    - 保存 `conversation_id`、`message_id`，以及每个带有 `id:` 的 Agent 事件的最新 SSE `id`。
    - 断线后使用同一个 API Key 和 `X-External-User-ID` 调用该接口。
    - 使用 `after_id` 续拉；如果客户端可能重试，请按 SSE `id` 去重。
    - 如果某个事件没有 SSE `id`，请把它视为不可恢复的降级事件，不要用作 `after_id`。
    - 收到 `message_end` 且状态为 `completed`、`stopped`、`error`、`failed`，或收到 `error` 后结束监听。

    ### 刷新页面与断线重连不是同一种恢复

    同一页面内网络中断时，客户端仍保有已经渲染的文本，可以携带最后一个 `after_id` 增量续拉，并按 SSE `id` 去重。页面刷新或应用重启后，不要只依赖本地游标：先加载消息历史，再对运行中或等待中的最新消息不传 `after_id` 从事件起点回放，用第一段 `message` 替换历史中的临时答案，后续分段再追加。

| 当前状态 | 判断依据 | 恢复动作 |
| --- | --- | --- |
| 运行中 | `runtime_status=running` 且有 `active_message_id` | 从事件起点回放并保持连接；同一页面再次断线后改用最新 `after_id` |
| 等待审批 | 最新消息 `status=waiting_approval` | 回放该消息以重建 `approval_requested`；也可先用消息 metadata 恢复表单作为即时 UI |
| 等待工作流回答 | `question_answer_requested`，或 `user_input_requested.source=agent_workflow_question_answer` | 渲染问题/选项并调用 workflow continuation |
| 等待 Skill 输入 | 其他 `user_input_requested` | 按问题 id 收集答案并调用 user-input continuation |
| 等待 Token 预算 | 最新消息为 `status=waiting_budget` | 展示独立预算操作，并使用对应 `request_id` 调用 token-budget continuation |
| 已完成或失败 | `completed`、`stopped`、`error`、`failed` | 只显示消息历史，不建立恢复流 |

    等待状态下会话通常已经不再是 `running`，因此不能只检查 `active_message_id`。还要检查最新消息的 `status`，并恢复同一个 `message_id`。事件过期后，非运行消息可能返回空 SSE；此时回退到消息 metadata。若 metadata 也缺少表单、动作或 request id，应显示“状态不可恢复”，不要猜测审批动作。

    ### 自动重连范例

    ```ts
    async function reconnectStream({ conversationId, messageId, lastEventId, signal }) {
      const seen = new Set<string>();
      let cursor = lastEventId;

      for (let attempt = 0; attempt <= 5; attempt += 1) {
        const query = new URLSearchParams({ message_id: messageId });
        if (cursor) query.set('after_id', cursor);
        const response = await fetch(
          `/api/v1/agents/conversations/${conversationId}/events?${query}`,
          { headers: agentHeaders, signal },
        );
        if ([400, 401, 403, 404].includes(response.status)) throw new Error('不可重试');
        if (!response.ok && response.status !== 429 && response.status < 500) throw new Error('不可重试');

        let terminal = false;
        try {
          await consumeSSE(response, (event) => {
            if (event.id && seen.has(event.id)) return;
            if (event.id) {
              seen.add(event.id);
              cursor = event.id;
            }
            renderAgentEvent(event);
            terminal = event.event === 'message_end' || event.event === 'error';
          });
          if (terminal) return;
        } catch (error) {
          if (signal.aborted) throw error;
        }
        if (attempt === 5) throw new Error('自动恢复次数已用尽');
        await delay(Math.min(800 * 2 ** attempt, 8000), signal);
      }
    }
    ```

    只有网络错误、`429` 和可恢复 `5xx` 应使用指数退避。聊天 POST 的结果不确定时不要重新 POST；取得 conversation/message id 后始终改用 events 接口。

  </Col>

## Agent 事件接入手册

产物标记 `access_mode: authenticated` 时不返回 `url` 或 `download_url`。
请使用同一 API Key 和最终用户身份，通过会话文件接口获取文件内容；不要根据
`file_id` 拼接公开 ToolFile 链接。

本节是聊天、断线恢复和继续接口共用的 SSE 契约。先根据原生 `event:` 分发，再读取 JSON envelope 的 `data.data`。不要把整个响应当成一个 JSON，也不要等连接关闭后再渲染。

### 推荐客户端状态机

1. 收到 `message_start` 就保存响应头或事件里的 `conversation_id`、`message_id`。
2. 收到带 `id` 的事件就立即持久化最新 id，并按 id 去重。
3. 可见答案只由 `message`、`message_retract`、`message_end.answer` 驱动；进度事件不要拼入最终答案。
4. `message_end.status` 为 `completed`、`stopped`、`error`、`failed` 时结束；为 `waiting_approval`、`waiting_question` 或 `waiting_budget` 时保留同一消息并走匹配的继续接口。
5. 断线后调用 events 接口恢复，不要重复提交原聊天请求。

<CodeGroup title="TypeScript 事件分发骨架">

```ts
type AgentEvent = { event: string; data: Record<string, unknown> };

function applyAgentEvent(frame: AgentEvent) {
  const data = frame.data;
  switch (frame.event) {
    case 'message_start':
      saveMessageIdentity(String(data.conversation_id), String(data.message_id));
      break;
    case 'message':
      appendAnswer(String(data.message_id), String(data.answer ?? ''));
      break;
    case 'message_retract':
      retractCandidate(String(data.message_id), String(data.presentation_disposition));
      break;
    case 'user_input_requested':
    case 'approval_requested':
    case 'question_answer_requested':
      renderPendingInteraction(frame);
      break;
    case 'token_budget_requested':
      renderTokenBudgetActions(frame);
      break;
    case 'message_end':
      transitionMessage(String(data.message_id), String(data.status));
      break;
    case 'error':
      showSafeError(String(data.message ?? 'Agent 执行失败'));
      break;
    default:
      updateOptionalProgress(frame); // 未识别事件必须安全忽略
  }
}
```

| `message_start`   | 助手消息记录创建后、回答文本之前      | 立即保存会话和消息 id；初始化空回答                                | `parent_id`, `title`, `model`, `replace`, `created_at` |
| `message`         | 模型产生新的可见回答片段              | 按 `message_id` 将 `answer` 追加到当前回答                         | `answer`                                               |
| `message_retract` | 已发送的候选文本不再属于最终回答      | `process` 时移出最终回答并可放入过程区；`discard` 时直接删除       | `presentation_disposition`, `answer?`                  |
| `message_end`     | 当前 SSE 阶段结束                     | 根据 `status` 进入终态或等待态；若有 `answer` 可用它校准完整文本   | `status`, `metadata`, `answer?`                        |
| `error`           | 流式传输或 runtime 产生客户端安全错误 | 展示 `message`；记录 `code`；若后续没有 `message_end` 则按失败终止 | `message`, `code?`, `params?`                          |

`message_start.parent_id` 为空表示根消息；`replace=true` 表示重新生成正在替换原分支结果。`message_end.status` 的终态为 `completed`、`stopped`、`error`、`failed`，等待态为 `waiting_approval`、`waiting_question`、`waiting_budget`。`metadata` 是公开扩展对象，客户端只读取已知字段并保留未知字段兼容性。

### Agent 绑定工作流事件

工作流事件用于执行轨迹和等待交互；最终助手文本仍只由核心消息事件维护。下面每个事件都使用通用 envelope，并按“关键字段”增加工作流字段。

| 事件                        | 含义与客户端动作                         | 关键字段                                                                                                                                |

### 公开等待状态如何继续

| 请求事件 / source | `message_end.status` | 保存什么 | 调用什么 |
| --- | --- | --- | --- |
| `approval_requested` | `waiting_approval` | `conversation_id`, `message_id`、顶层 `approval_token`、`ui_approval_allowed`、嵌套 `approval_form` 与所选 `action` | workflow continuation，`type=approval` |

继续请求返回的仍是同一条消息的 SSE 流，可能再次等待。不要新建消息；持续处理到真正终态。普通已发布工具仍为非交互授权；仅服务端准入的 Linux 平台 CLI 调用可通过 `tool_governance_decision.requires_approval=true` 要求专用 tool-governance 续接。审批不能补足资源权限，也不会重跑 Shell。

## JSON 错误响应

SSE 建立之前，所有接口都以匹配的 HTTP 状态返回 JSON 错误。`code` 是稳定的 ZGI 错误码，`message` 是面向客户端的安全描述；校验错误可能使用更具体的文字，客户端应容忍新增字段。

<Properties>
  <Property name="code" type="string" propKey="code">
    机器可读错误码；成功为 `0`，错误为非零值。
  </Property>
  <Property name="message" type="string" propKey="message">
    可展示或记录的安全错误描述。
  </Property>
</Properties>

<CodeGroup title="错误响应" label="400 JSON">

```json
{ "code": "199001", "message": "Invalid parameter" }
```

</CodeGroup>

- `400`：JSON/参数/id/枚举非法，缺少外部用户，Memory revision 过期，或旧 `user` 与请求头不一致。
- `401`：API Key 缺失、错误、已停用、已过期或已撤销。
- `403`：已认证调用者没有该操作权限。
- `404`：没有发布版本、资源不属于当前用户、Memory 槽位不存在，或继续请求已过期/已处理。
- `409`：runtime 状态或乐观并发冲突（后端单独映射时）。
- `500`：服务内部错误；不要向最终用户暴露上游或内部细节。

## 重试、安全与跨域

- 推荐架构是“浏览器 → 你的 BFF/服务端 → ZGI”，由服务端注入 API Key。即使部署允许你的 Origin 跨域，也不要把 Key 下发给浏览器。
- 建立 SSE 前若返回 `4xx/5xx`，按普通 JSON 错误处理；已建立流后按 `error` / `message_end` 处理。只对网络错误、`429` 和可恢复的 `5xx` 使用指数退避，不要自动重试 `400/401/403/404`。
- 对聊天 POST 的不确定重试可能创建重复消息。收到 `message_start` 后优先通过 events 接口恢复；客户端按 SSE `id` 去重。
- 机器可读契约位于 `/api/openapi.yaml`，交互式页面位于 `/swagger/index.html`。

## 注意事项

- 该接口始终运行 Agent 的最新发布版本，不能调用草稿配置。
- API Key 只能访问它绑定的 Agent。
- 多轮上下文使用 `conversation_id`，流恢复、两类 continuation 和重新生成使用 `message_id`，排查工作流节点事件使用 `workflow_run_id`。
- 完整的 Next.js 服务端代理、SSE 状态机和页面接线示例见仓库 `docs/agent-api-quickstart.md`。
