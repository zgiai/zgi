# 数字人 API

使用当前数字人的最新发布版本构建品牌化、可恢复的聊天体验。接口只支持流式响应；能复用 Agent 外接语义的部分保持一致，同时显式保留数字人的 Durable Run 生命周期。

## 接入总览

### 鉴权与终端用户身份

只在服务端发送数字人 API Key：

<CodeGroup title="请求头" targetCode={`Authorization: Bearer {api_key}`}>

```text
Authorization: Bearer {api_key}
```

</CodeGroup>

API Key 不能进入浏览器代码、移动端安装包、日志、分析系统或 URL。所有有状态请求还必须传 `user`：最长 128 字符、稳定、不透明、大小写敏感的业务用户标识。

| 概念              | 用途                           | 稳定性规则                            |
| ----------------- | ------------------------------ | ------------------------------------- |
| API Key           | 鉴权调用方和数字人             | 可轮换，不改变用户数据归属            |
| `user`            | 拥有会话、文件、运行和关系记忆 | 稳定、大小写敏感、不能包含个人信息    |
| `request_id`      | 保证一次聊天请求幂等           | 只在重试同一载荷时复用                |
| `run_id`          | 跟踪 Durable Run 和断线恢复    | 由响应头及 `run_accepted` 返回        |
| `conversation_id` | 维持多轮上下文                 | 同一 `user` 后续请求继续使用          |
| `message_id`      | 标识本轮助手消息               | 由 `message_start` 返回并进入历史记录 |

一个 Key 可以服务多个终端用户。Key 轮换后，同一 `user` 的数据身份不变；不同 `user` 之间完全隔离，同一字符串在不同数字人下也不是同一主体。请勿使用邮箱、手机号等直接身份信息，原始 `user` 不会在响应中返回。

### 推荐浏览器架构

```text
浏览器或移动端 UI
        |
        | 业务系统登录态
        v
你的 BFF / API Route  -- 仅服务端持有 Key -->  ZGI /api/v1/digital-humans/*
        |
        +-- 从登录态派生稳定 `user`
        +-- SSE 原样转发且禁止缓冲
        +-- 执行授权、限流和请求大小限制
```

浏览器不应接触 Key，也不应自行指定另一个账号的 `user`。历史、恢复、停止、运行时输入和文件上传等所有代理路由，都要从同一登录态派生 `user`。

### 最小生产闭环

1. 读取 `/digital-humans/config`，渲染标题、开场白、建议问题、输入提示和主题色。
2. 生成 UUID `request_id`，调用 `/digital-humans/chat`，立即保存 `X-ZGI-Run-ID`。
3. 增量解析 SSE，保存 `conversation_id`、`message_id` 和最近一个非空事件 `id`。
4. 追加 `message.data.answer`；`message_end` 结束消息阶段；唯一的 `run_end` 结束 Durable Run。
5. 断线后使用相同 `user`、保存的 `run_id` 和 `Last-Event-ID` 恢复；收到 `message_start` 后不要重发聊天 POST。
6. 页面刷新后先读取消息历史，再决定是否恢复仍在运行的 Run。

## 构建高质量 Demo

下面的客户端核心不依赖框架，能够处理拆分的 SSE 帧、多行 data、未知事件、恢复游标和终态：

```ts
export type ZGIEvent<T = Record<string, unknown>> = {
  id?: string;
  event: string;
  data: T;
};

export async function readZGISSE(
  response: Response,
  onEvent: (event: ZGIEvent) => void
): Promise<void> {
  if (!response.ok) {
    const error = await response.json().catch(() => ({
      code: `http.${response.status}`,
      message: response.statusText,
      retryable: response.status === 429 || response.status >= 500,
    }));
    throw Object.assign(new Error(error.message), { status: response.status, ...error });
  }
  if (!response.body) throw new Error('ZGI 返回了空事件流');

  const reader = response.body.getReader();
  const decoder = new TextDecoder();
  let buffer = '';

  while (true) {
    const { value, done } = await reader.read();
    buffer += decoder.decode(value, { stream: !done }).replace(/\r\n/g, '\n');
    const frames = buffer.split('\n\n');
    buffer = frames.pop() ?? '';

    for (const frame of frames) {
      let id: string | undefined;
      let nativeEvent = 'message';
      const dataLines: string[] = [];
      for (const line of frame.split('\n')) {
        if (line.startsWith('id:')) id = line.slice(3).trim();
        else if (line.startsWith('event:')) nativeEvent = line.slice(6).trim();
        else if (line.startsWith('data:')) dataLines.push(line.slice(5).trimStart());
      }
      if (!dataLines.length) continue;
      const envelope = JSON.parse(dataLines.join('\n')) as {
        event?: string;
        data?: Record<string, unknown>;
      };
      onEvent({ id, event: envelope.event ?? nativeEvent, data: envelope.data ?? {} });
    }
    if (done) break;
  }
}
```

推荐使用 reducer 管理状态，不要把运行状态散落在各个回调中：

```ts
type ChatState = {
  phase: 'idle' | 'accepting' | 'streaming' | 'waiting' | 'completed' | 'error';
  runId?: string;
  conversationId?: string;
  messageId?: string;
  lastEventId?: string;
  answer: string;
  error?: string;
};

function applyZGIEvent(state: ChatState, event: ZGIEvent): ChatState {
  const data = event.data;
  const cursor = event.id || state.lastEventId;
  switch (event.event) {
    case 'run_accepted':
      return { ...state, phase: 'accepting', runId: String(data.run_id), lastEventId: cursor };
    case 'message_start':
      return {
        ...state,
        phase: 'streaming',
        conversationId: String(data.conversation_id),
        messageId: String(data.message_id),
        answer: data.replace ? '' : state.answer,
        lastEventId: cursor,
      };
    case 'message':
      if (state.messageId && data.message_id !== state.messageId) return state;
      return { ...state, answer: state.answer + String(data.answer ?? ''), lastEventId: cursor };
    case 'message_end': {
      const status = String(data.status);
      return {
        ...state,
        phase: status.startsWith('waiting_')
          ? 'waiting'
          : status === 'completed'
            ? 'completed'
            : 'error',
        lastEventId: cursor,
      };
    }
    case 'error':
      return {
        ...state,
        phase: 'error',
        error: String(data.message ?? '请求失败'),
        lastEventId: cursor,
      };
    case 'run_end':
      return {
        ...state,
        phase: data.status === 'succeeded' ? 'completed' : state.phase,
        lastEventId: cursor,
      };
    default:
      return { ...state, lastEventId: cursor };
  }
}
```

## 数字人事件接入手册

### 通用信封和恢复字段

ZGI 同时发送原生 SSE `event:` 和相同事件名的 JSON 信封：

```text
id: 1715750400000-0
event: message
data: {"event":"message","data":{"conversation_id":"...","message_id":"...","answer":"你好"}}
```

可根据 JSON `event` 或原生 SSE event 分发。事件 ID 是不透明字符串；客户端必须忽略未知事件名和未知字段，保持向前兼容。

| 事件            | 客户端必须执行                                              | Durable 含义          |
| --------------- | ----------------------------------------------------------- | --------------------- |
| `run_accepted`  | 保存 `run_id`、`request_id`、`status`、`created`            | 幂等请求已受理        |
| `message_start` | 保存 `conversation_id`、`message_id`；处理 `replace`        | 持久化助手消息已创建  |
| `message`       | 为匹配的消息追加 `answer`                                   | 可恢复的回答增量      |
| `message_end`   | 解释消息 `status` 和 `metadata`                             | 当前消息阶段结束      |
| `error`         | 展示安全 `message`；存在时记录 `code`；检查可选 `retryable` | HTTP 200 后的流式错误 |
| `run_end`       | 停止恢复并记录最终 `status`                                 | 唯一 Durable 终态事件 |

### 状态与恢复矩阵

| 已观察状态                              | UI 状态        | 下一步                                                          |
| --------------------------------------- | -------------- | --------------------------------------------------------------- |
| Chat 已受理，尚无 `message_start`       | 启动中         | 保持 POST 流，保存 `run_id`                                     |
| 已收到 `message_start`                  | 生成中         | 渲染增量并保存最近 SSE id                                       |
| Run 未终止但网络断开                    | 重连中         | 通过 Run Events 和 `Last-Event-ID` 恢复                         |
| `message_end=completed`，尚无 `run_end` | 收尾中         | 继续监听到 `run_end`                                            |
| `message_end=waiting_*`                 | 暂不支持的交互 | 保留标识并展示安全兜底；数字人 v1 尚未开放审批/问题专用续接接口 |
| `run_end` 携带终态                      | 已终止         | 停止重连，以历史记录为准                                        |

页面完全刷新后先读取消息历史。Run 仍在执行时，不要假设浏览器保存的游标与全新 DOM 已渲染内容一致；应按非空 SSE id 及 `(message_id, event id)` 去重。

## JSON 错误、重试与安全

SSE 建链前，错误使用 HTTP 状态码和安全 JSON：

```json
{ "code": "digital_human.request.invalid", "message": "Invalid request.", "retryable": false }
```

| HTTP  | 常见原因                                    | 自动重试               |
| ----- | ------------------------------------------- | ---------------------- |
| `400` | UUID 非法、`user` 缺失/非法、响应模式不支持 | 否                     |
| `401` | Key 缺失、无效、过期、停用或撤销            | 否                     |
| `403` | API Surface 或部署总开关关闭                | 否                     |
| `404` | Run、会话、消息或发布版本不在调用方范围     | 否                     |
| `409` | 幂等载荷或 Durable 状态冲突                 | 先校准状态再决定       |
| `413` | 上传超过请求上限                            | 否                     |
| `415` | 文件类型不支持                              | 否                     |
| `429` | 速率或上游限流                              | 有上限的指数退避       |
| `500` | 内部失败                                    | 仅 `retryable=true` 时 |

HTTP 200 的 SSE 开始后，应消费 `error` 和 `run_end`，不会再有第二个 HTTP 状态码。日志只记录安全 `code`、`run_id` 和业务侧请求追踪 ID；不得记录 API Key、原始 `user`、提示词、文件内容或模型输出。
