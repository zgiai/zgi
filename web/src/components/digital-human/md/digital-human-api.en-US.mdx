# DigitalHuman API

Use this API to build a branded, recoverable chat experience on the latest published version of this DigitalHuman. The API is streaming-only. Its contract follows the Agent external API where the runtime semantics match, while keeping the DigitalHuman durable `run_id` lifecycle explicit.

## Integration Overview

### Authentication and end-user identity

Send the DigitalHuman API key from your server:

<CodeGroup title="Headers" targetCode={`Authorization: Bearer {api_key}`}>

```text
Authorization: Bearer {api_key}
```

</CodeGroup>

Never put the key in browser code, a mobile binary, logs, analytics, or a URL. Every stateful request also sends `user`, a stable opaque business identifier with at most 128 characters.

| Concept           | Meaning                                                  | Stability rule                                     |
| ----------------- | -------------------------------------------------------- | -------------------------------------------------- |
| API key           | Authenticates the integration and DigitalHuman           | May be rotated without moving user data            |
| `user`            | Owns conversations, files, runs, and relationship memory | Stable, case-sensitive, non-PII value              |
| `request_id`      | Makes one chat request idempotent                        | Reuse only when retrying the same payload          |
| `run_id`          | Tracks durable execution and stream recovery             | Returned by the response header and `run_accepted` |
| `conversation_id` | Continues multi-turn context                             | Reuse for later chat requests from the same `user` |
| `message_id`      | Identifies the assistant message                         | Returned by `message_start` and stored in history  |

One key may serve many end users. The same `user` remains the same data subject after key rotation, but is isolated from other `user` values and from the same value used with another DigitalHuman. Do not use email addresses or phone numbers. The raw value is not returned.

### Recommended browser topology

```text
Browser or mobile UI
        |
        | your authenticated session
        v
Your BFF / API route  -- server-only API key -->  ZGI /api/v1/digital-humans/*
        |
        +-- derives a stable `user`
        +-- streams SSE without buffering
        +-- enforces authorization, rate limits, and request-size limits
```

The browser sends no API key and should not be allowed to choose another account's `user`. Derive `user` from your authenticated session on every proxy route, including history, recovery, stop, runtime input, and file upload.

### Minimum production flow

1. Fetch `/digital-humans/config` and render `home_title`, `opening_statement`, `suggested_questions`, and `input_placeholder`.
2. Generate a UUID `request_id`, send `/digital-humans/chat`, and save `X-ZGI-Run-ID` immediately.
3. Parse SSE incrementally. Save `conversation_id`, `message_id`, and the latest non-empty SSE `id`.
4. Append `message.data.answer`; finish the message on `message_end`; finish durable execution on the single `run_end`.
5. If the connection drops, recover with the saved `run_id`, same `user`, and `Last-Event-ID`. Do not repeat the chat POST after `message_start`.
6. After a page refresh, load conversation messages before opening a recovery stream.

## Build a High-Quality Demo

The following client core is framework-neutral and handles split SSE frames, multi-line data, unknown events, recovery cursors, and terminal states.

```ts
export type ZGIEvent<T = Record<string, unknown>> = {
  id?: string;
  event: string;
  data: T;
};

export async function readZGISSE(
  response: Response,
  onEvent: (event: ZGIEvent) => void
): Promise<void> {
  if (!response.ok) {
    const error = await response.json().catch(() => ({
      code: `http.${response.status}`,
      message: response.statusText,
      retryable: response.status === 429 || response.status >= 500,
    }));
    throw Object.assign(new Error(error.message), { status: response.status, ...error });
  }
  if (!response.body) throw new Error('ZGI returned an empty stream');

  const reader = response.body.getReader();
  const decoder = new TextDecoder();
  let buffer = '';

  while (true) {
    const { value, done } = await reader.read();
    buffer += decoder.decode(value, { stream: !done }).replace(/\r\n/g, '\n');
    const frames = buffer.split('\n\n');
    buffer = frames.pop() ?? '';

    for (const frame of frames) {
      let id: string | undefined;
      let nativeEvent = 'message';
      const dataLines: string[] = [];
      for (const line of frame.split('\n')) {
        if (line.startsWith('id:')) id = line.slice(3).trim();
        else if (line.startsWith('event:')) nativeEvent = line.slice(6).trim();
        else if (line.startsWith('data:')) dataLines.push(line.slice(5).trimStart());
      }
      if (!dataLines.length) continue;
      const envelope = JSON.parse(dataLines.join('\n')) as {
        event?: string;
        data?: Record<string, unknown>;
      };
      onEvent({ id, event: envelope.event ?? nativeEvent, data: envelope.data ?? {} });
    }
    if (done) break;
  }
}
```

Use a reducer instead of scattering stream state across UI callbacks:

```ts
type ChatState = {
  phase: 'idle' | 'accepting' | 'streaming' | 'waiting' | 'completed' | 'error';
  runId?: string;
  conversationId?: string;
  messageId?: string;
  lastEventId?: string;
  answer: string;
  error?: string;
};

function applyZGIEvent(state: ChatState, event: ZGIEvent): ChatState {
  const data = event.data;
  const cursor = event.id || state.lastEventId;
  switch (event.event) {
    case 'run_accepted':
      return { ...state, phase: 'accepting', runId: String(data.run_id), lastEventId: cursor };
    case 'message_start':
      return {
        ...state,
        phase: 'streaming',
        conversationId: String(data.conversation_id),
        messageId: String(data.message_id),
        answer: data.replace ? '' : state.answer,
        lastEventId: cursor,
      };
    case 'message':
      if (state.messageId && data.message_id !== state.messageId) return state;
      return { ...state, answer: state.answer + String(data.answer ?? ''), lastEventId: cursor };
    case 'message_end': {
      const status = String(data.status);
      return {
        ...state,
        phase: status.startsWith('waiting_')
          ? 'waiting'
          : status === 'completed'
            ? 'completed'
            : 'error',
        lastEventId: cursor,
      };
    }
    case 'error':
      return {
        ...state,
        phase: 'error',
        error: String(data.message ?? 'Request failed'),
        lastEventId: cursor,
      };
    case 'run_end':
      return {
        ...state,
        phase: data.status === 'succeeded' ? 'completed' : state.phase,
        lastEventId: cursor,
      };
    default:
      return { ...state, lastEventId: cursor }; // forward-compatible progress event
  }
}
```

## DigitalHuman Event Integration Guide

### Common envelope and recovery fields

ZGI sends a native SSE `event:` plus a JSON envelope with the same event name:

```text
id: 1715750400000-0
event: message
data: {"event":"message","data":{"conversation_id":"...","message_id":"...","answer":"Hello"}}
```

Dispatch by the JSON `event` or native SSE event. Treat event ids as opaque strings. Ignore unknown event names and unknown fields for forward compatibility.

| Event           | Required client behavior                                                      | Durable meaning                       |
| --------------- | ----------------------------------------------------------------------------- | ------------------------------------- |
| `run_accepted`  | Save `run_id`, `request_id`, `status`, and `created`                          | The idempotent request is accepted    |
| `message_start` | Save `conversation_id` and `message_id`; honor `replace`                      | A persistent assistant message exists |
| `message`       | Append `answer` for the matching message                                      | Recoverable answer delta              |
| `message_end`   | Interpret message `status` and `metadata`                                     | Current message phase ended           |
| `error`         | Show safe `message`; record `code` when present; inspect optional `retryable` | Stream failed after HTTP 200          |
| `run_end`       | Stop recovery and record final run `status`                                   | Single durable terminal event         |

The same event names and payload families used by the Agent API are available for a richer process UI:

| Event family                | Events                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                      | Recommended rendering                                                                                                      |
| --------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------- |

### State and recovery matrix

| Observed state                            | UI state                | Next action                                                                                                          |
| ----------------------------------------- | ----------------------- | -------------------------------------------------------------------------------------------------------------------- |
| Chat accepted, no `message_start` yet     | Starting                | Keep the POST stream open; retain `run_id`                                                                           |
| `message_start` received                  | Generating              | Render deltas and save the latest SSE id                                                                             |
| Network drops while run is non-terminal   | Reconnecting            | Call Run Events with `Last-Event-ID`                                                                                 |
| `message_end=completed`, no `run_end` yet | Finalizing              | Keep listening until `run_end`                                                                                       |
| `message_end=waiting_approval`            | Task approval         | Replace the composer with the approval form and continue the original message through workflow-continuation; do not send a new natural-language confirmation |
| `message_end=waiting_question`            | User input            | Keep the ids and render the question control described by `user_input_requested` |
| `message_end=waiting_budget`              | Token budget          | Render the independent `token_budget_requested` actions and call token-budget continuation |
| `run_end` with a terminal status          | Terminal                | Stop reconnecting; history is the source of truth                                                                    |

On a full page reload, fetch conversation messages first. If a run is still active, reconnect without assuming that a locally stored cursor matches what the fresh DOM rendered. De-duplicate by non-empty SSE id and by `(message_id, event id)`.

When a conversation creates or changes a task, the run pauses in
`waiting_approval`. Read the approval form from `approval_requested` or message
metadata, replace the composer with the approval controls, and submit
`POST /api/v1/digital-humans/conversations/{conversation_id}/messages/{message_id}/workflow-continuation` with the same `user`, `approval_token`, and `action`. Continue consuming SSE events for the same message after the approval completes.

When the stream ends in `waiting_question` and emits `user_input_requested`,
submit the answer to
`POST /api/v1/digital-humans/conversations/{conversation_id}/messages/{message_id}/user-input/{request_id}/continue` with the same `user` and an `answers` object keyed by question id. This resumes the original Agent Loop in place; do not send a new chat message or route it through workflow-continuation.

When the stream ends in `waiting_budget`, handle the independent
`token_budget_requested` event. Call
`POST /api/v1/digital-humans/conversations/{conversation_id}/messages/{message_id}/token-budget/{request_id}/continue`
with the same `user` and either `{"action":"add","additional_tokens":2048}` or
`{"action":"stop"}`. Do not send `answers`; stopping produces a normal
`message_end(status=stopped)` rather than a generic error.

Read, update, and action a task using its `revision`.

Supported actions are `confirm`, `decline`, `run_now`, `pause`, `resume`,
`retry`, `cancel`, and `archive`. A stale revision returns
`409 digital_human.task.conflict`; refresh and retry with the latest revision.
`GET /digital-humans/tasks/{task_id}/runs?user=customer_123` returns bounded
run metadata and a safe `result_summary`, never execution traces or model
responses. Activities redact trusted actor references such as API key ids.

When a conversation proposes or changes a task, the SSE emits
`approval_requested` and the message enters `waiting_approval`. Replace the
composer with the approval form and call
`POST /digital-humans/conversations/{conversation_id}/messages/{message_id}/workflow-continuation`
with the same `user`, `approval_token`, and `action`; do not send a second
natural-language “confirm” message.

Authenticated landing pages expose equivalent
`/api/v1/digital-human-webapps/{web_app_id}/tasks...` endpoints. They derive
the account subject from the signed session and do not accept a browser
`user`. Anonymous sessions cannot create tasks or register task tools.

## JSON Errors, Retries, and Security

Before SSE starts, errors use the HTTP status plus a safe JSON body:

```json
{ "code": "digital_human.request.invalid", "message": "Invalid request.", "retryable": false }
```

| HTTP  | Typical cause                                                   | Automatic retry                  |
| ----- | --------------------------------------------------------------- | -------------------------------- |
| `400` | Invalid UUID, missing/invalid `user`, unsupported response mode | No                               |
| `401` | Missing, invalid, expired, inactive, or revoked key             | No                               |
| `403` | API surface or deployment gate disabled                         | No                               |
| `404` | Run, conversation, message, or publication outside caller scope | No                               |
| `409` | Idempotency payload or durable state conflict                   | Only after reconciling state     |
| `413` | Upload exceeds the request limit                                | No                               |
| `415` | Unsupported file type                                           | No                               |
| `429` | Rate or upstream limit                                          | Yes, bounded exponential backoff |
| `500` | Internal failure                                                | Only when `retryable=true`       |

After HTTP 200 SSE begins, consume `error` and `run_end`; there is no second HTTP status. Log safe `code`, `run_id`, and your own request trace id—never the API key, raw `user`, prompts, uploaded content, or model output. Apply timeouts separately to connection establishment and inactive streams, keep proxy buffering disabled, and rate-limit per authenticated user rather than per shared API key alone.

## Notes

- The API runs the latest published version. Draft configuration is never exposed.
- An API key can access only the DigitalHuman it is bound to.
- Relationship memory follows the same `user` identity but has no public management endpoint in this release.
- Root-message regeneration and editing are available through the conversation SSE endpoint; `regenerate_enabled` is `true`. Non-root messages should be replayed as a new branch with `parent_message_id`.
- The machine-readable contract is available at `/api/digital-human-openapi.yaml`.
